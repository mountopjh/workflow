# 执行方案撰写指南（EXECUTION_PLAN_WRITING_GUIDE）

> 本指南给**项目维护者**看。回答"怎么写一份能直接喂给工作流跑的 EXECUTION_PLAN.md"。  
> 配套模板：`templates/EXECUTION_PLAN.md`。

---

## 0. 一句话定位

**执行方案 = 把"PRD + 技术文档"翻译成"按环节、按工单、按步骤的施工序列"。**

- PRD 回答**为什么做 / 做什么** → `docs/PRD.md`
- 技术文档回答**用什么方案、按什么架构落地** → `docs/TECH_DESIGN.md`
- 执行方案回答**按什么顺序施工、每步做什么、做完判定标准是什么** → `docs/EXECUTION_PLAN.md` ← 本指南讲的就是它

执行方案是**规划师拆单的唯一依据**——AI 看的是这份文件，不是 PRD 和技术文档。

---

## 1. 顶层结构（必有）

每份执行方案必须包含以下四块，顺序固定：

```
1. 元信息
2. 全局约定（规划师必读）
3. 变更日志
4. 环节 1 / 环节 2 / ... / 环节 N
```

---

## 2. 元信息（必填字段）

放在文档最前面：

| 字段 | 必填 | 说明 | 示例 |
|---|:---:|---|---|
| 版本 | ✅ | 执行方案本身的版本号；每次修订递增 | `V1.0` |
| 生成时间 | ✅ | 你定稿/修订的时间 | `2026-05-16 14:30:22` |
| 关联 PRD 版本 | ✅ | 本方案对应的 PRD 版本号 | `PRD V1.0` |
| 关联技术文档版本 | ✅ | 本方案对应的技术文档版本号 | `TECH_DESIGN V1.0` |
| 总环节数 | ✅ | Phase 总数 | `5` |
| 预估总工单数 | ✅ | 所有环节预估工单数之和 | `18` |

> **作用**：规划师启动时会校验"`PLAN_INDEX.md` 中记录的方案版本"与"本文件版本"是否一致。不一致 → 走 ESCALATE 等人工介入，避免拿着旧方案发新单。

---

## 3. 全局约定（必写一次）

写在所有环节之前，告诉规划师**这份方案的写作规则**：

- **本方案"步骤"颗粒度**：每步 = 工单的 1 个任务点（≤ 1 个动作）
- **技术文档引用规则**：本方案不重复技术文档内容；引用形式必须是 `参照 TECH_DESIGN.md §X.Y`
- **作者保留实现细节决定权**：`true` / `false`
  - `false` → 执行者按自己理解实现
  - `true` → 关键步骤会附"实现要点"子项，执行者必须遵守
- **跨环节状态约定**：环节间只通过文件 / 数据库 / 接口传递；禁止依赖前一环节的临时变量、内存对象等
- **正在执行的环节不允许修改步骤清单**：等该环节走到 PASS 或 ESCALATE 后再改

---

## 4. 变更日志（必写）

固定结构，新条目写在顶部：

```
## 变更日志
- V1.2（2026-05-18 09:14:33）：环节 3.5 增加 1 步（添加日志埋点）；总工单数 18→19
- V1.1（2026-05-17 16:42:08）：环节 2.3 修正文件路径
- V1.0（2026-05-16 14:30:22）：首版
```

**版本号语义**：
- **小修补**（步骤微调、文件路径修正）：patch +1（V1.0 → V1.1）
- **环节增减或重排**：minor +1（V1.0 → V2.0）
- **整体重写**（PRD 大改导致方案重做）：major +1（V1.0 → V2.0）

---

## 5. 环节（Phase）的必填结构

每个环节固定 6 段：

```
## 环节 N · <环节名>

### N.1 环节目标（一句话）
### N.2 前置条件
### N.3 验收基线（环节级别）
### N.4 工单切分（含工单数预估、是否打 tag）
### N.5 步骤清单（按工单拟切分）
### N.6 风险与备注
```

### 5.1 §N.1 环节目标
**一句话写清楚"这个环节做完后可独立验收的产出是什么"**。

- ✅ "完成用户鉴权模块：登录、登出、Token 刷新三个 API 可被前端调用并通过集成测试"
- ❌ "做用户系统"（太泛）
- ❌ "实现 JWT + Redis 缓存 + 7 天 Token 有效期"（写到了实现，越界）

### 5.2 §N.2 前置条件
列出本环节启动前必须满足的条件：

```
- [需要的环境/依赖/前一环节产出]
- 关联前置环节：环节 N-1（若有）
```

例：
> - 数据库已建好 user 表（环节 1 产出）
> - Redis 已部署可用
> - 关联前置环节：环节 1

### 5.3 §N.3 验收基线（环节级别）
环节级别的"做完了吗"判定，比单个工单的验收点更高一层：

```
- 产出文件清单：<具体路径>
- 自动化测试要全绿：<命令>
- 关键场景手测项：<可选>
```

### 5.4 §N.4 工单切分

```
- 预估工单数：3
- 是否打 Git tag：是 / 否
- tag 名（如打）：phase-N-done
```

**约束**：
- 所有环节"预估工单数"之和 = 元信息"预估总工单数"，不一致 = 写错
- 环节做完最后一单且打 tag = 是 → 大总管自动 `git tag phase-N-done`
- 推荐每个环节都打 tag，方便回溯

### 5.5 §N.5 步骤清单（最关键）

按工单切分，每个工单是一个独立的 ≤ 5 步骤的小块：

```
#### 工单 1（≤5 步）
- [ ] 步骤 1：做什么 / 在哪做 / 验收点 / 引用 TECH_DESIGN §X.Y（如有）
- [ ] 步骤 2：...
- 预计授权文件：
  - <项目根>/src/<具体路径>.<ext>
  - <项目根>/tests/<具体路径>.<ext>
- 适用红线：R1, R3, R7
```

**每个工单必填**：
- 步骤清单（≤ 5 条，每条有 `[ ]` 复选标记）
- 预计授权文件（≤ 5 个，必须是具体路径，禁通配）
- 适用红线（来自 `config/redlines_index.md`）

### 5.6 §N.6 风险与备注
本环节已知的风险点 / 与其他环节的耦合点 / 妥协说明。  
若有"事实违反"红线的妥协，必须显式声明。

## 6. 单个步骤的内容规范（最关键）

### 6.1 "3 要 3 不要"

| 必须有 | 必须没有 |
|---|---|
| ✅ **做什么**（动作 + 对象） | ❌ **怎么做**（实现细节是技术文档的责任） |
| ✅ **在哪做**（具体文件路径或模块名） | ❌ **为什么这么做**（理由属于 PRD/技术文档） |
| ✅ **验收点**（一句话能判断完成与否） | ❌ **形容词验收**（"用户友好""高性能"无法验收） |

### 6.2 反例 vs 正例

| 反例 | 正例 |
|---|---|
| "优化登录性能" | "在 src/auth/login.py 实现登录令牌缓存：命中缓存时跳过 DB 查询；通过 tests/auth/test_login_cache.py 单测全绿" |
| "做一下数据校验" | "在 src/validators/user_input.py 增加邮箱格式校验函数 validate_email；通过 tests/validators/test_email.py 中 5 个用例" |
| "重构那段代码" | "把 src/order/checkout.py 中第 80-150 行的折扣计算逻辑提取到 src/order/discount_strategy.py；调用方保持原签名；checkout 测试不变全绿" |
| "用 Redis 缓存登录态 30 秒" | "在 src/auth/session.py 实现 SessionStore 接口（参照 TECH_DESIGN §3.2）；通过 tests/auth/test_session.py 全部用例" |

> 倒数第二条：缓存策略写在技术文档里。执行方案只引用 §X.Y。

### 6.3 颗粒度参考

- **单步 = 单动作**：好的步骤通常 1-2 行能写完
- **多个动作 = 拆多步**：如果一步要写 4-5 行才能讲清楚，应当拆
- **跨文件不算多步**：同一逻辑动作涉及多个文件，作为一步写没问题（但授权文件清单要列全）

---

## 7. 全份方案硬约束

| 约束 | 详情 |
|---|---|
| **总长度** | 建议 ≤ 1500 行；超长说明环节没拆好 |
| **工单数对齐** | 所有环节 §N.4 "预估工单数"之和 = 元信息"预估总工单数" |
| **环节编号连续** | 1, 2, 3...不跳号；增删时整体重排 |
| **复选标记** | 每个步骤前必须有 `[ ]`，方便人类追踪进度 |
| **跨环节代码引用** | 禁止。环节 N 要改环节 M 创建的文件 → 必须在自己 §N.5 的"预计授权文件"里重新列出 |
| **禁含完整代码** | 出现 ≥ 10 行代码块 = 越界。代码是执行者的产出，不是方案的内容 |

---

## 8. 工作流读取规则（你不需要管，但要知道）

### 规划师每次唤醒会做：
1. 读元信息确认 PRD/技术文档版本对得上
2. 读全局约定
3. 找当前焦点对应的环节 → 按 §N.5 的工单切分发出 1 个 `CURRENT_TASK.md`

### 你改了执行方案会怎样：
- 改了**未执行**的环节 → 下次规划师唤醒时直接生效，不需要重启工作流
- 改了**正在执行**的环节 → 违反铁律，规划师可能拿着旧切分发了新单，结果是 REJECT 后再修
- 改了元信息中的版本号 → `PLAN_INDEX.md` 上记录的"关联执行方案版本"会对不上 → 规划师走 ESCALATE 等人工修订 PLAN_INDEX

## 9. 实战检查清单（写完执行方案后过一遍）

提交前自检：

- [ ] 元信息 6 字段全填
- [ ] 全局约定段写了 5 项
- [ ] 变更日志至少有 V1.0 一条
- [ ] 环节编号连续，无跳号
- [ ] 每个环节 6 段（§N.1 ~ §N.6）齐全
- [ ] 所有 §N.4 "预估工单数"之和 = 元信息"预估总工单数"
- [ ] 每个步骤都包含"做什么 + 在哪做 + 验收点"三要素
- [ ] 每个步骤都有 `[ ]` 复选标记
- [ ] 没有任何步骤写"怎么做"（实现细节）
- [ ] 没有任何形容词验收（"友好"、"快速"、"安全"）
- [ ] 每个工单的"预计授权文件" ≤ 5 个，且是具体路径不是通配
- [ ] 每个工单的"适用红线"是 `redlines_index.md` 中存在的编号
- [ ] 涉及实现细节的地方都引用了 `TECH_DESIGN.md §X.Y`
- [ ] 没有任何 ≥ 10 行的代码块

全部 ✅ 后才算可发布。

## 10. 常见问答

**Q: 执行方案要写到多细？**  
A: 写到"执行者拿着这单 + 技术文档 §X.Y 就能直接动手"的程度。再细就侵犯了执行者的实现自由；再粗规划师就拆不出工单。

**Q: 一个环节一定要打 git tag 吗？**  
A: 不一定。短环节（< 3 工单）可以不打。长环节、里程碑环节、对外发布前环节建议打。

**Q: 步骤里能不能直接给代码片段做示例？**  
A: 不行。短伪代码（≤ 3 行）描述算法可以接受；超过就是越界。完整代码片段属于技术文档或执行者的产出。

**Q: 一份方案最多多少环节合适？**  
A: 经验值 3-8 个环节，每环节 3-6 个工单，总工单数 15-40 之间。超过 50 单建议拆成多份方案分阶段交付。

**Q: 改了 PRD 但执行方案还能用吗？**  
A: 看 PRD 改了什么。改硬约束 → 必须重做执行方案；改功能范围 → 至少改对应环节；改性能基线 → 改 §N.3 验收基线。所有情况下都要更新元信息 `关联 PRD 版本`。

**Q: 执行方案能不能边写边跑？**  
A: 可以。先写完前 1-2 个环节就启动工作流跑，后续环节边跑边补。但每次新增环节后要更新元信息（总环节数、总工单数）和变更日志。

## 11. 一份合规执行方案的最小样例骨架

参见同目录下的 `EXECUTION_PLAN.md` 模板。把它复制到 `<项目根>/docs/EXECUTION_PLAN.md` 后照着填空即可。
