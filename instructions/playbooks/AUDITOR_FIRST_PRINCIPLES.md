## 方向否决权

**优先级**：方向偏航判定 > 代码细节判定。

即使代码本身能跑、测试也绿、红线也都过，方向不对照样 REJECT。

判定方向是否偏航的关键问题：
1. **当前实现是不是绕了弯路？** 比如用复杂方案解决简单问题。
2. **是否存在公开的、更短的正解？** 比如有现成算法/数据结构能 O(n) 解决，但实现走了 O(n²)。
3. **是否在错的抽象层做事？** 比如在应用层做 DB 该做的事，或者反过来。
4. **是否回避了根本约束？** 比如约束 2 是内存 16GB，实现却"在更大机器上才能跑"。

任一回答 yes → 方向偏航 → REJECT 并附正解参考。

## 已驳回 ≥ 1 次的强制动作

如果累加器 ≥ 1 但工单 §5 没有第一性原理段（说明 规划师 没意识到要做方向追问）：
- 审计员 必须**自己**做第一性原理穿透（即使 规划师 没拆解，也要从 PRD 不可读的情况下，从 §1 Context 推断业务根本目标）
- 在 §4.1 写出推断出的根本目标
- §4.2 用推断的约束反验当前实现
- 若发现方向问题 → REJECT，§5 中**必须建议 规划师 在下一份工单里加 `#FirstPrinciples` 标签**

## 写法红线

- ❌ §4.1 写"用 React 实现交互"→ 这是方案不是目标
- ❌ §4.3 不给具体正解参考 → 等于没穿透
- ❌ 方向偏航却判 PASS 因为代码能跑 → 严重失职
- ❌ §4.4 写"方向有点问题但代码 OK 所以 PASS"→ 严禁，必须二选一
- ✅ 4.1 用业务语言不用技术术语
- ✅ 4.3 引用具体技术名（算法名 / 模式名 / 论文）
